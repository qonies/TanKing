# 系统模式（System Patterns）

> 详细架构设计见 `docs/02-技术路线.md`。

## 总体架构：客户端-服务器，服务器权威
```
┌──────────┐   WebSocket    ┌───────────────────┐   WebSocket   ┌──────────┐
│ 浏览器 A  │ ◄────────────► │  Node.js 主机进程   │ ◄───────────► │ 浏览器 B  │
│ 输入上报  │   输入(上行)    │  · 房间/大厅管理     │  状态快照(下行) │ 输入上报  │
│ 快照渲染  │                │  · 60Hz 游戏模拟    │               │ 快照渲染  │
└──────────┘                │  · AI 机器人        │               └──────────┘
                            │  · 静态文件托管(HTTP) │
                            └───────────────────┘
```

## 关键设计决策
1. **服务器权威（Server Authoritative）**：单一大厅进程内嵌游戏模拟器；客户端是"哑终端"，只发输入、收快照。杜绝状态分歧，逻辑只写一份。
2. **固定时间步长模拟**：服务器以固定 60Hz tick 模拟世界；快照按 tick 序号广播，客户端缓冲 2~3 帧做插值渲染，消除网络抖动。
3. **输入驱动协议**：上行只传按键位掩码（1~2 字节），下行快照做字段级增量（局域网内带宽充裕，优先简单可靠的 JSON，必要时再切二进制）。
4. **逻辑与渲染分离**：`shared/` 纯逻辑模块（实体、碰撞、地图）不依赖 DOM/Node API，可被 Vitest headless 测试。
5. **状态机驱动流程**：客户端（Menu → Lobby → Playing → Result）与房间（Waiting → Countdown → Playing → RoundEnd）均为显式状态机，消息只允许合法状态迁移。

## 组件关系
- `GameServer`（房间管理 + tick 循环 + 消息路由）
- `BattleSim`（单局模拟：实体、碰撞、道具、AI、计分）
- `GameClient`（连接管理、输入采集、快照插值、渲染、音频）
- `MapLoader`（JSON 关卡 ↔ 网格数据）
