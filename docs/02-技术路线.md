## 1. 总体架构

**客户端-服务器（C/S），服务器权威（Server Authoritative）。**

```
浏览器客户端（×N）                          Node.js 主机（房主机器）
┌─────────────────────────┐               ┌──────────────────────────────┐
│ Input（键盘采集）          │   上行：输入    │  HTTP: 静态文件托管（前端构建产物） │
│ Renderer（快照插值→Canvas）│ ◄──────────► │  WS:  消息路由 + 房间状态机        │
│ Audio                    │   下行：快照    │  GameServer: tick 循环           │
│ InterpBuffer(2~3帧)      │               │  BattleSim: 单局模拟（权威世界）    │
└─────────────────────────┘               │  BotController: AI 决策           │
                                          └──────────────────────────────┘
```

### 1.1 核心原则
1. **服务器权威**：所有移动、碰撞、伤害、道具、计分、AI 决策都在服务器模拟；客户端是哑终端，只上报输入、渲染快照。无状态分歧问题，逻辑单点，天然防作弊。
2. **逻辑/渲染分离**：游戏逻辑（实体、碰撞、地图、道具效果、计分）放在 `shared/` 纯 TypeScript 模块，不依赖 DOM 或 Node API —— 前端（单机模式、地图预览渲染）与服务器引用同一份代码，Vitest 可 headless 测试。
3. **固定时间步长**：服务器以固定 dt（1/60s）推进模拟，与真实帧率解耦；网络抖动用时间累积器吸收。
4. **流程即状态机**：客户端 `Menu → Lobby → Playing`（结算用覆盖层展示，无独立 Result 状态）；房间 `Waiting → Countdown → Playing → RoundEnd → …`。协议消息只在合法迁移时被接受。

## 2. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | TypeScript（前后端统一） | 类型安全；`shared/` 代码双端复用 |
| 前端构建 | Vite | 开发热更新快，产物即静态文件 |
| 渲染 | 原生 Canvas 2D API，不引入游戏引擎 | 游戏本身极简（tile + sprite），引擎（Phaser 等）反而是负担；原版逻辑分辨率 416×416，`ctx.imageSmoothingEnabled=false` + 整数倍缩放 |
| UI 层 | 轻量 DOM（菜单/大厅/HUD 计分板）或纯 Canvas | 倾向 DOM 做 UI、Canvas 做战场，开发效率高 |
| 音频 | Web Audio API | 原生支持合成/采样，8-bit 音效可用方波/噪声合成 |
| 服务端 | Node.js ≥ 20 + `ws` | `ws` 轻量可控（Socket.IO 的降级/重连特性在局域网内不需要） |
| 进程模型 | 单 Node 进程：`node:http` 原生静态服务（`server/http.ts`）+ `ws` 共享 HTTP 端口 | 一条命令、一个端口完成部署；不引入 Express/Fastify |
| 测试 | Vitest（单元/集成）+ Playwright（E2E） | Vitest 原生 TS 支持；Playwright 可多页面对象模拟多人联机 |

**备选被否方案**：
- *WebRTC P2P*：免服务器但需要信令、ICE，局域网内增加复杂度；且权威服务器架构下信令服务器照样要跑 —— 不如直接 WebSocket。
- *状态同步改为帧同步（Lockstep）*：要求确定性浮点/随机，实现与调试成本高；局域网快照同步（~KB/s）完全够用。

## 4. 网络协议设计

### 4.1 传输与格式
- WebSocket（文本 JSON 起步；对局快照若 profiling 显示瓶颈再切二进制 `DataView`，局域网内 JSON 预计足够）。
- 消息统一信封：`{ t: 消息类型, ...载荷 }`。

### 4.2 消息一览

| 方向 | 类型 | 载荷 | 频率 |
|---|---|---|---|
| C→S | `join` | 昵称（单房间，无房间字段） | 进房时 |
| C→S | `input` | 1 字节输入位掩码（`INPUT_UP/DOWN/LEFT/RIGHT/FIRE`，见 `shared/constants.ts`） | 变化时发送 + 15 tick 心跳兜底 |
| C→S | `chat`、`config`（房主设置总坦克数/AI 难度/地图/积分上限/回合时长/道具开关）、`start` 等 | — | 事件 |
| S→C | `lobbyState` | 房间成员/配置/地图预览；对局与结算阶段额外携带 `map` + `terrain`（重连地形同步）、`ticksLeft`、`roundResult`（胜者 + 排名） | 变化时 |
| S→C | `snapshot` | tick 序号 + 全量实体状态（位置为像素浮点，1.5px 步进；坦克含 kills/deaths）+ `ticksLeft`（回合剩余，FR-U3） | 每 tick（60Hz） |
| S→C | `event` | 击杀播报、道具拾取、爆炸、音效触发、回合开始/结束 | 事件 |

### 4.3 同步细节
- **快照**：局域网带宽充裕，全量快照实测 ≈1.44KB/tick（8 实体），60Hz × 8 连接 ≈ 0.67MB/s，局域网无压力；留增量优化余地。
- **客户端插值**：维护快照缓冲，渲染时刻 = 最新快照 tick − 2（约 33ms 缓冲），在两帧快照间线性插值位置 —— 平滑消除网络抖动。
- **无需客户端预测**（局域网 RTT < 10ms，缓冲后感知延迟 ≈ 45ms，满足 NFR-2 的 50ms）；若实测手感不佳，再对**本地坦克**加输入预测 + 服务器校正。
- **断线**：WebSocket `close` → 玩家标记掉线 → 坦克交给 BotController 托管 → 60s 内**同名 `join`** 可重连续局（无 token，同名即接管，PRD FR-N4 尽力而为方案）。重连时 `lobbyState` 携带当前地图名与完整地形数组，客户端据此重建 TerrainView。

## 5. 服务器模拟（BattleSim）

- **tick 循环**：`setInterval` 不精确，用 `setTimeout(1)` 忙等 + 累积器，每 tick 消耗固定 1/60s 虚拟时间；追帧上限防雪崩。
- **实体**：Tank（玩家/AI 统一）、Bullet、PowerUp、Base（全局唯一中立基地）、Terrain Grid（26×26 小格单元位图）。
- **移动**：半格对齐 —— 按键期间自由像素移动，松开/转向时吸附到最近半格（还原原版手感的关键）。
- **碰撞**：AABB；子弹 vs 地形按小格单元判定损毁（砖 1/4 格、L3 连带整格）；子弹 vs 子弹相互抵消；坦克 vs 坦克互为障碍。
- **随机数**：种子化 PRNG（mulberry32）由服务器持有，用于 AI 决策与道具刷新，保证可复现（利于测试回放）。
- **AI**：BotController 每 tick 产出虚拟输入（与真人玩家同一 `input` 通道），决策含：随机巡逻、朝最近目标（玩家/道具；无敌人可追踪时概率性攻打基地）BFS 寻路（在 26×26 网格上）、遇障碍变向、视线内开火。难度调决策频率/精度/抢道具意愿。

## 6. 渲染方案（客户端）

- 逻辑分辨率 416×416（26 小格 × 16px 或等效），Canvas CSS 尺寸整数倍放大；`imageSmoothingEnabled = false`。
- 图层顺序（自底向上，与 renderer.ts 实现一致）：地面 → 冰面/水面 → 基地/道具 → 子弹 → 坦克（护盾/冻结）→ 砖/钢 → 树林（最上层遮挡）→ 爆炸特效 → HUD（DOM）。
- 精灵表：自制 sprite sheet（PNG），索引表由构建脚本生成；爆炸为 3~5 帧序列。
- 单机模式：客户端直接实例化 `shared/sim/BattleSim` 本地跑，无网络 —— 联机与单机天然共用逻辑。

## 7. 关卡与数据

- 地图 JSON：`{ name, size: 26, terrain: ["26 行字符矩阵"], spawns: [...], base: {...}, powerupSpots: [...] }`。`size` 为小格数（26 小格 = 13 大格 × 2）；`terrain` 为**顶层字段**（字符矩阵，非 layers 嵌套）；`base` 为全局唯一中立基地。loader 校验：尺寸、出生点越界/重复/落在实体地形、基地越界/被地形覆盖、道具点越界/落在实体地形。
- 内置 6 张 PvP 对战地图（原版经典关卡布局改编 + 独创）。
- 参数表（`constants.ts`）：坦克速度/子弹速度/弹量/升级数值，以及计分规则（1 击杀 = 100 分、基地 +500 分、坦克道具 +200 分、满级星星 +100 分）等，需在 M1 期间对照原版逐项核定（建 `docs/参数对照表.md`）。

## 8. 测试基建

- 单元测试（Vitest，headless）：`shared/sim` 全覆盖 —— 移动吸附、碰撞、地形破坏、道具效果、计分；PRNG 种子固定保证可复现。
- 集成测试（Vitest + Node）：直接实例化 `Room`（房间状态机）+ fake 客户端 socket，跑完整回合流程。
- E2E（Playwright）：启动真实服务器 → 打开 2~3 个浏览器页 → 加入同一房间 → 断言各自进入对局、击杀计分同步（详见 `docs/03-测试文档.md`）。

| M4 多人体验 | 8 坦克房间（真人 + AI 合计）、AI 3 档难度、大厅聊天、键位自定义、断线托管 | M2、M3 |
| M5 发布打磨 | 性能验证、Windows 防火墙说明、部署脚本、测试全绿 + 发布前复审修复（L3 四方向/结算可见性/回合配置/容错，2026-10-21） | 全部 |

**最大风险与对策**：
1. *原版手感偏差* → M1 先做"参数对照表"+ 与模拟器原版逐帧比对，作为验收项。
2. *浏览器多开 E2E 不稳* → Playwright 每用例独立 browser context，CI 仅跑冒烟，全量本地跑。
3. *素材产能* → 素材是人力瓶颈，M1 只需最小集；可用临时占位色块先行，视觉迭代后置。
